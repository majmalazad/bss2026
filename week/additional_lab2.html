Tutorial overview

Path traversal occurs when an application places external input into a file-system path without ensuring that the final resolved path remains inside an approved directory. An attacker can use parent-directory elements, alternate encodings, absolute paths or platform-specific separators to reach files that the application was not intended to expose.

This practical uses VulnShop’s Help Centre, invoice download function and local AI assistant. Students first establish normal behaviour, identify the file-selection parameters, demonstrate controlled access to supplied mock files, examine common filtering obstacles, automate testing with Burp Suite, and then apply secure design principles.

Learning outcomes

  • Explain relative and absolute path traversal and how path normalisation changes the final file location.

  • Identify user-controlled filename and path parameters in web requests.

  • Use Burp Proxy, Repeater and Intruder to validate a path traversal condition.

  • Distinguish a confirmed vulnerability from a missing validation control or an unhelpful error response.

  • Explain URL encoding, double encoding, nested traversal sequences and extension restrictions.

  • Map the finding to CWE-22 and discuss confidentiality, integrity and availability impact.

  • Apply allowlist mapping, canonical-path checks and least-privilege controls.

  • Document evidence using only supplied mock teaching data.

Real-world cyber security and job-market connection

Path traversal testing is common in web and API assessments because applications frequently process filenames, templates, reports and downloads. You will learn to prove boundary escape, assess impact and verify a secure fix.

Where you will use it: These skills support Web Penetration Tester, Application Security Analyst, Secure Code Reviewer and Vulnerability Research roles.

Concepts and security impact

Understand path resolution, the threat model, CIA impact and the VulnShop attack surface.

1. Concept and threat model

Many web features need to read a server-side file: a help article, product image, invoice, template, language pack or report. A vulnerable design accepts a path or filename from the request, joins it to a base directory, and opens the result without checking where the operating system ultimately resolves it.

1.1 Example: an unsafe image-loading request

Consider a web application that loads an image from a filename supplied in the URL. A normal request asks the server to read an approved image:

/loadImage?filename=gift.png
StageNormal requestPath traversal request
User inputgift.png../../../../etc/passwd
Application behaviourThe application joins the value to its approved image folder.The application joins the untrusted value without checking the final resolved path.
File-system resultThe operating system reads the intended image.Each ../ moves to a parent directory. The final path can escape the image folder and reach a sensitive file.
Security effectThe user receives the requested image.The attacker may read files available to the web application process, causing a confidentiality breach.

Conceptual example only. The image illustrates the attack with /etc/passwd. In this practical, you must use only the local VulnShop instance and the supplied mock files.

1.2 Conditions required for exploitation

  • The application accepts a filename, path fragment or file identifier from an untrusted source.

  • The value reaches a file-reading or file-writing API.

  • The application does not use a strict mapping of permitted identifiers to files.

  • The application does not canonicalise the final path and enforce the approved directory boundary.

  • The application process has permission to access the targeted file.

Authorisation boundary

A successful payload in VulnShop does not authorise testing against other websites. Every task in this tutorial is limited to 127.0.0.1 and the supplied mock files.

2. How paths are resolved

2.1 Relative traversal

The sequence ../ means “use the parent directory” on Unix-like systems. If a file is expected under help_pages/, the value ../server_private/server_credentials.txt moves from help_pages/ to its parent and then enters server_private/.

Intended base directory:
/opt/vulnshop/help_pages/

User-controlled value:
../server_private/server_credentials.txt

Combined path before normalisation:
/opt/vulnshop/help_pages/../server_private/server_credentials.txt

Resolved path:
/opt/vulnshop/server_private/server_credentials.txt

2.2 Absolute traversal

An absolute path begins from the file-system root or another platform-defined root. Some path-joining APIs discard the intended base directory when the second value is absolute. The VulnShop Help Centre strips leading slashes as a safety measure, but a production application must not treat this as sufficient validation.

2.3 Platform differences

Environment Common separator behaviour Teaching observation
Linux / Unix / separates directories; ../ refers to the parent. VulnShop runs on Kali Linux and uses forward slashes.
Windows Both \ and / may be accepted by application or file-system APIs. A test plan should include both separator styles when the target platform is Windows.
URL layer Reserved path characters can be percent-encoded. The server or framework may decode input before application validation.

Do not test real system files

The lab deliberately supplies .htaccess, mock_shadow.txt, server_credentials.txt and ai_support_notes.txt. Use these files instead of /etc/passwd, /etc/shadow or other operating-system data.

3. Security impact

Path traversal is primarily associated with unauthorised file access, but the impact depends on the operation performed by the vulnerable feature and the permissions of the application process.

Security property Possible consequence VulnShop example
Confidentiality Read source code, configuration, keys, credentials, logs or personal data. Read the supplied mock credential note or mock shadow-style file.
Integrity Overwrite templates, configuration, scripts or application data when a write operation is exposed. The current Help Centre exercise is read-only; file-upload filename handling is a separate integrity risk.
Availability Delete, replace or corrupt files needed by the service. Not enabled in the path traversal exercise.

3.1 Related weakness categories

Weakness Relationship
CWE-22 General path traversal: the final path escapes a restricted parent directory.
CWE-23 Relative path traversal using elements such as ../.
CWE-36 Absolute path traversal using a path rooted outside the expected directory.
CWE-73 External control of a filename or path may be the broader input-control condition.
CWE-209 Detailed file-system errors can reveal internal paths and assist payload construction.

Risk depends on permissions

The same coding error has different impact when the application runs as a restricted service account than when it runs with broad file-system access.

10. URL encoding and decoding behaviour

Browsers, proxies, frameworks and application code may decode input at different stages. A useful test records the raw URL and the value the application displays or processes.

Task 9 - Test an encoded traversal sequence

http://127.0.0.1:5000/help?page=%2e%2e%2fserver_private%2fserver_credentials.txt

Expected result: Flask decodes the value to ../server_private/server_credentials.txt and the supplied mock file is displayed.

Task 10 - Test double encoding

http://127.0.0.1:5000/help?page=%252e%252e%252fserver_private%252fserver_credentials.txt

Expected result in the current setup: the application sees %2e%2e%2f... rather than ../..., so the file is not found.

Testing lesson

A failed double-encoded payload does not prove the input is safe. It shows only that this path currently receives one relevant decoding pass.

11. Common obstacles and bypass patterns

Applications often attempt to stop traversal using partial filtering or format requirements. The current VulnShop route demonstrates basic and URL-encoded traversal. The additional patterns below support analysis and test-plan design; not every pattern is expected to work in this lab.

Obstacle Test idea Why it may matter
Traversal sequences removed once Try a nested pattern such as ....// in an authorised test environment. Removing an inner sequence can leave a new ../ sequence after filtering.
Leading traversal blocked Test an absolute path only when the scope explicitly permits it. Some path APIs discard the base directory when the supplied value is absolute.
URL layer strips ../ Try percent-encoded and, where justified, double-encoded forms. Filtering may happen before or after decoding.
Input must start with a base directory Include the required prefix followed by parent-directory elements. A string-prefix check is not a canonical boundary check.
Input must end with an extension Test whether the parser validates the real final path or only the string suffix. Legacy null-byte handling and inconsistent parsers historically allowed suffix bypasses; modern runtimes often reject null bytes.
Windows target Test both ../ and ..\. Backslash may be interpreted as a directory separator.

Avoid indiscriminate payloads

Use only payloads needed to answer the authorised test question. Automated lists can create noisy logs, expose unintended files or trigger availability problems.

15. Validation checklist and false positives

Check Evidence or decision
Scope The target is the local VulnShop instance on 127.0.0.1.
Controllable input The request contains a page, file or filename value controlled by the tester.
File operation The value reaches a server-side read function.
Boundary escape The successful value resolves outside help_pages/ or invoices/.
Known file content The response matches a supplied mock file.
Reproducibility The request succeeds consistently and the baseline still works.
Impact The report links the weakness to the type of file exposed.
Mitigation retest Normal approved files work, while traversal variants are rejected.

15.1 Common false-positive conditions

  • The application reflects the filename in an error page but never reads a file.

  • Every request returns the same generic page, cache entry or custom 200 error response.

  • The returned text is generated by the application and does not match a real supplied file.

  • A missing validation control exists, but the process cannot access any file outside the intended directory.

  • A scanner reports a traversal pattern without proving a meaningful path resolution or response difference.

Professional evidence

Redact session cookies and avoid including unnecessary file contents. A short excerpt, hash or clear mock-file marker can be enough to prove the result.

16. Root cause in the VulnShop code

The Help Centre accepts the page query parameter, removes only leading slash characters, joins it to HELP_DIR, and opens the result. No canonical path or allowlist check is performed.

@app.route("/help")
def help_centre():
    page = request.args.get("page", "returns.txt").lstrip("/\\")
    path = os.path.join(HELP_DIR, page)
    with open(path, "r", encoding="utf-8", errors="replace") as f:
        content = f.read()

16.1 Why the current check is insufficient

  • lstrip("/\\") prevents a leading separator but leaves parent-directory sequences inside the value.

  • os.path.join() constructs a string; it does not enforce a security boundary.

  • The final path is not resolved and compared with HELP_DIR.

  • The user controls both directory elements and the final filename.

The invoice route has the same root cause:

filename = request.args.get("file", "invoice_alice.txt")
path = os.path.join(INVOICE_DIR, filename)
return send_file(path, as_attachment=False)

Avoid superficial fixes

Blocking only the literal string ../ can be bypassed by alternate separators, encoding, inconsistent decoding or future code changes. Validate the final meaning of the path.

Final teaching message

Path traversal is not merely the presence of dots in a URL. The security failure occurs when external input controls a file path and the application does not enforce the intended directory after the path is fully resolved.

Secure design and retesting

Apply identifier mapping or canonical-path validation, then confirm that approved functionality still works.

17. Secure design: map fixed identifiers to files

The safest design avoids accepting a path from the user. The browser sends a limited identifier, and the server maps it to a filename that is controlled by the application.

HELP_PAGES = {
    "returns": "returns.txt",
    "delivery": "delivery.txt",
    "warranty": "warranty.txt",
}

@app.route("/help")
def help_centre():
    page_id = request.args.get("page", "returns")
    filename = HELP_PAGES.get(page_id)
    if filename is None:
        abort(404)

    path = os.path.join(HELP_DIR, filename)
    with open(path, "r", encoding="utf-8") as handle:
        content = handle.read()

    return render_template("help.html", page=page_id, content=content)

17.1 Benefits

  • The user cannot supply directory separators or an arbitrary filename.

  • Business rules are explicit: only three approved help topics exist.

  • File locations can change without exposing internal directory structure in URLs.

  • Logging and access-control decisions can use meaningful identifiers.

Preferred approach

When the valid set of files is known, use identifier-to-file mapping rather than trying to sanitise a free-form path.

18. Secure design: canonicalise and enforce the base directory

Some applications legitimately need a larger set of filenames. In that case, validate the input and verify the final resolved path after joining it to the approved directory.

from pathlib import Path
from flask import abort

BASE_DIR = Path(HELP_DIR).resolve()

def approved_file(user_value: str) -> Path:
    if not user_value or user_value.startswith(("/", "\\")):
        abort(400)

    candidate = (BASE_DIR / user_value).resolve()

    try:
        candidate.relative_to(BASE_DIR)
    except ValueError:
        abort(403)

    if not candidate.is_file():
        abort(404)

    return candidate

18.1 Additional controls

  • Use least-privilege operating-system permissions so the service cannot read unrelated sensitive files.

  • Reject directory separators when the feature requires only a simple filename.

  • Decode once into a documented internal representation before validation; avoid inconsistent double decoding.

  • Do not expose full server paths in user-facing errors.

  • Log rejected traversal attempts without recording secrets.

  • Store sensitive application files outside directories reachable by file-serving features.

19. Retesting the corrected design

A fix is complete only when approved functionality still works and the original proof of concept no longer crosses the directory boundary.

Test Expected secure result
/help?page=returns or the approved application format Returns article is displayed.
../server_private/.htaccess Rejected with a controlled 400, 403 or 404 response.
../server_private/server_credentials.txt Rejected; no private file content appears.
%2e%2e%2fserver_private%2fserver_credentials.txt Rejected after decoding and canonical validation.

21. Independent challenge lab

Scenario

A new local document-viewer route accepts a file identifier and returns one of several teaching documents. The instructor has not told you whether it uses a fixed mapping, filename filtering or canonical-path validation.

Student objectives

1. Locate the route through normal application use and identify the parameter controlling the document.

2. Record a normal baseline request and known response content.

3. Test the minimum relative traversal needed to reach one supplied mock file.

4. Test a URL-encoded equivalent and explain the decoding result.

5. Use Repeater to confirm the result and Intruder only with a short lab-specific list.

6. Identify the most appropriate CWE and describe the confidentiality impact.

7. Propose an allowlist or canonical-path correction.

8. Repeat the proof of concept after the correction and document the result.

Hints

  • Look for parameter names such as page, file, filename, template, document, report or language.

  • Compare response length and unique text, but open the responses before drawing a conclusion.

  • Count directory levels from the intended base to the supplied private file.

  • A 200 response does not always mean success; a 404 response does not always mean the value was safely rejected.

Challenge outcome

Record a concise finding in your lab notes. Include one redacted Burp request, the supplied mock-file marker, the primary CWE, the confidentiality impact, the proposed correction and the secure retest result.
