Additional Lab 6

Business Logic Vulnerabilities

Trust boundaries, semantic validation, workflow enforcement and complete business state

Duration: approximately 3 hoursTarget: http://127.0.0.1:5000Platform: Kali Linux and Burp Suite

Authorised laboratory use only. Complete every activity against the supplied local VulnShop instance on 127.0.0.1. Do not test public websites, university services, live shops or third-party accounts.

Overview and learning outcomes

A business logic vulnerability occurs when an application follows a rule or workflow in a way that permits an unintended outcome. The request may be syntactically valid and the user may be authenticated. The weakness appears because the application trusts the wrong value, accepts an impossible condition, applies a rule inconsistently or permits steps in the wrong order.

Core idea

Start by stating the intended business rule. Then ask what happens when a value, state transition or sequence does not match the developer's assumption.

By the end of this lab, you should be able to

  • Explain how business logic flaws differ from input-injection vulnerabilities.
  • Identify security-relevant values that cross the browser–server trust boundary.
  • Use Burp Proxy, HTTP history and Repeater to capture and modify authorised requests.
  • Test price, quantity, profile, workflow and coupon assumptions in VulnShop.
  • Compare a normal baseline with manipulated behaviour and final application state.
  • Explain confidentiality, integrity, availability and business impact.
  • Recommend server-side validation, state-machine and transaction controls.

Real-world cyber security and job-market connection

Business logic flaws often evade automated scanners because the tool cannot understand the organisation's intended prices, account roles, payment stages or promotion rules. Professionals find these weaknesses by mapping the workflow, questioning assumptions and proving a business effect rather than relying only on unusual HTTP responses.

Where you will use it: You will apply these skills in Web Penetration Tester, Application Security Analyst, Product Security Engineer, Security Consultant, Fraud and Abuse Analyst, Secure Software Engineer and Security-focused QA roles.

Human reasoning matters.

A scanner may record HTTP 200 without recognising that a customer bought an £89.99 product for £1.00, gained staff access through an unverified email or confirmed an order without payment. Always interpret the result in the context of the intended business rule.

For every experiment, record

  • The intended rule.
  • The normal baseline request and final state.
  • The single value or sequence you changed.
  • The manipulated response and final application state.
  • The CIA and business impact.
  • The server-side fix and one regression test.

Experiment 1

Excessive trust in a client-controlled price

A hidden input is not secret or trustworthy. Burp can change the value before it reaches the server.

3. Manipulate the submitted product price

The Secure Laptop Bag is displayed at £89.99. The account has £35.00 credit, so the normal order should fail. VulnShop incorrectly calculates the total using a hidden price field supplied by the browser.

Part A — Establish the baseline

  1. Open http://127.0.0.1:5000/business-logic/client-price.
  2. Reset the experiment.
  3. With interception off, add one item and select Place order.
  4. Confirm that the server rejects the £89.99 order because it exceeds the £35 credit.

Part B — Change only the price

  1. Reset the experiment and turn interception on.
  2. Add one Secure Laptop Bag.
  3. Locate the submitted price parameter:
POST /business-logic/client-price/add HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/x-www-form-urlencoded price=89.99&quantity=1

Change only the price:

price=1.00&quantity=1
  1. Forward the request and switch interception off.
  2. Confirm that the basket shows a submitted unit price of £1.00.
  3. Select Place order and verify that the order succeeds.
ObservationMeaning
The catalogue displays £89.99The application knows the authoritative product price.
The request contains price=89.99A transaction-critical value crosses the client boundary.
Changing the value changes the totalThe server uses the submitted value instead of loading the database price.
Checkout accepts £1.00The rule is bypassed and an unintended financial transaction occurs.

Secure design: Send a stable product identifier and quantity, load the current price from server-side storage, recalculate the total at checkout and reject missing, negative, non-finite or out-of-range values.

Experiment 2

High-level logic flaw using a negative quantity

HTML min=1 improves usability, but it cannot prevent a modified request from containing an impossible value.

4. Reduce the basket total with a negative quantity

The account has £40 credit. A Smart Door Camera costs £89.99 and a Password Notebook costs £3.99. VulnShop accepts negative integers and includes them in the calculation:

£89.99 + (-13 × £3.99) = £38.12
  1. Open http://127.0.0.1:5000/business-logic/negative-quantity and reset the experiment.
  2. Add one Smart Door Camera normally.
  3. Set the Password Notebook quantity to 1, turn interception on and submit the form.
  4. Modify the captured body:
POST /business-logic/negative-quantity/add HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/x-www-form-urlencoded product=notebook&quantity=-13
  1. Forward the request and return interception to off.
  2. Confirm a notebook quantity of −13, a line total of −£51.87 and a cart total of £38.12.
  3. Place the order and verify that the server accepts the impossible basket.

Why this is a semantic flaw

The request is valid form data and the server can parse the integer. The problem is that a purchase quantity cannot be negative. Validation must check meaning, not only syntax.

Additional inputQuestionExpected secure behaviour
quantity=0Can an order contain a zero-value line?Reject or remove the line.
quantity=-1Can the server accept a negative purchase quantity?Reject before changing the basket.
Very large integerCan arithmetic, stock or resource limits be exceeded?Apply maximum and stock validation.
Non-integer valueHow does parsing fail?Return a controlled error without changing state.

Secure design: Validate quantity as an integer within a defined server-side range, check stock and customer limits, reject non-positive line totals and use decimal-safe money calculations.

Experiment 3

Inconsistent security controls

A security rule must run whenever trusted identity data changes. A new email address must not inherit trust without verification.

5. Gain staff access through an unverified email

VulnShop treats an email ending in @vulnshop.local as proof that an account belongs to staff. The profile update process changes the email and immediately recalculates access without verifying ownership.

  1. Open http://127.0.0.1:5000/business-logic/inconsistent-controls and reset the experiment.
  2. Select Open staff area and confirm that the server denies access, normally with HTTP 403.
  3. Change the profile email to:
alice@vulnshop.local
  1. Save the profile and confirm that the page reports Staff access: Granted.
  2. Open the staff area again and verify that protected supplier information is now visible.

Request analysis

POST /business-logic/inconsistent-controls HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/x-www-form-urlencoded email=alice%40vulnshop.local

The value is not an injection payload. The flaw lies in assuming that an authenticated user owns any replacement email address entered later.

Impact areaExample
ConfidentialityStaff-only supplier or administrative information becomes visible.
IntegrityA customer may perform protected staff actions.
AvailabilityPrivileged functions could disrupt accounts, products or workflows.

Secure design: Verify ownership of each new email before using it for authorisation, keep identity attributes separate from roles, grant roles through an approved process and re-evaluate active sessions after security-relevant changes.

Experiment 4

Insufficient workflow validation

A final endpoint must verify current server-side state rather than assume that earlier steps occurred.

6. Replay a confirmation request without payment

Part A — Observe a legitimate workflow

  1. Open http://127.0.0.1:5000/business-logic/workflow and reset the experiment.
  2. Add the affordable Password Notebook and complete the normal purchase.
  3. In Proxy → HTTP history, locate the final request:
GET /business-logic/workflow/confirmation?order-confirmation=true HTTP/1.1 Host: 127.0.0.1:5000 Cookie: session=...
  1. Send this request to Repeater but do not resend it yet.

Part B — Bypass the payment step

  1. Add the Smart Door Camera, which costs £89.99 and exceeds the remaining credit.
  2. Attempt normal payment and confirm that the server rejects it.
  1. Return to Repeater and resend the saved confirmation request while the expensive camera remains in the basket.
  2. Refresh the workflow page and confirm that the camera appears as the last confirmed order with Payment step recorded: No.
State or checkSecure requirementVulnerable behaviour
Basket existsNecessary but not sufficientUsed as the only confirmation condition.
Payment authorisedMust match the current order and amountNot checked.
Transaction identifierValid, unique and bound to the orderNo transaction evidence required.
Endpoint replayFinalisation must be one-time and idempotentThe old request applies to a new basket.

Secure design: Use an explicit server-side state machine, bind payment evidence to the order, user and amount, require state PAID before CONFIRMED, reject replay and make finalisation idempotent.

Experiment 5

Flawed enforcement of coupon rules

A one-use rule must track complete redemption history. Comparing only with the immediately previous code is insufficient.

7. Bypass coupon reuse controls by alternating codes

The Prototype Payment Ring costs £129.99 and the account has £40 credit. NEWCUST10 gives 10% off and SIGNUP20 gives 20% off. The application blocks an immediate duplicate but remembers only the last code.

Part A — Identify the incomplete rule

  1. Open http://127.0.0.1:5000/business-logic/coupons and reset the experiment.
  2. Add the Prototype Payment Ring.
  3. Apply NEWCUST10 once.
  4. Apply NEWCUST10 again immediately and confirm that the second use is rejected.

Part B — Alternate the codes

Continue with this sequence:

SIGNUP20 → NEWCUST10 → SIGNUP20 → NEWCUST10 → SIGNUP20 → NEWCUST10 → SIGNUP20
  1. Observe that every code is accepted because it differs from the immediately previous code.
  2. Confirm that the total falls to approximately £34.93.
  3. Place the order and verify that both coupons were reused several times.
QuestionFinding
What is the intended scope of one use?The order, account, campaign, device or customer must be defined.
What state is stored?Only the most recently applied coupon.
Why does alternation work?The previous value differs even though the current code was redeemed earlier.
What should be stored?Every redeemed code, use counters and campaign constraints.
What else must be checked?Expiry, eligible products, minimum spend, account eligibility and maximum discount.

Secure design: Store redemption in authoritative server data, enforce uniqueness for the correct scope, apply a maximum total discount and evaluate campaign conditions inside a concurrency-safe transaction.

Defensive design

Consolidate root causes, impact and controls

Secure design keeps authoritative values and workflow state on the server and treats each transition as a rule that must be proved.

Server-side control checklist

  • Authoritative data: Load prices, roles, eligibility and order state from trusted storage.
  • Sensible values: Validate range, sign, format and relationships between fields.
  • Explicit state transitions: Define permitted moves and verify prerequisites.
  • Complete history: Track all relevant prior uses, not only the last request.
  • Atomic transactions: Validate and update financial or redemption state together.
  • Re-authentication and verification: Require fresh evidence for sensitive identity changes.
  • Monitoring: Alert on negative quantities, repeated discounts, abnormal totals and skipped steps.
  • Security testing: Include misuse cases and unexpected sequences in regression tests.

Suggested secure pseudocode

product = database.get_product(product_id) quantity = parse_integer(request.quantity) if quantity < 1 or quantity > MAX_PER_ORDER: reject("Invalid quantity") unit_price = product.current_price subtotal = money(unit_price * quantity) order = database.get_order(order_id, user_id) if order.state != "PAID": reject("Payment required") if coupon_code in order.redeemed_coupons: reject("Coupon already used") confirm_order_in_atomic_transaction(order)

Independent practice

Challenge lab — test an assumption without the walkthrough

Choose one experiment and investigate it from the stated business rule before reading its step-by-step instructions.

9. Complete the business logic challenge

Scope. Use one local experiment only. Reset it before testing and keep all requests on 127.0.0.1:5000.

  1. Write the intended rule in one sentence.
  2. Capture a normal request and identify the parameters or server state that support the rule.
  3. Create at least three misuse cases, including one boundary value and one unusual sequence.
  4. Use Repeater to test one controlled change at a time.
  5. Record the baseline and manipulated application state.
  6. Explain why the result is a business logic flaw rather than merely unusual input.
  7. Propose a server-side fix and a regression test.
