Additional Lab 5

Race Condition Attack

Limit overrun, rate-limit bypass and single-endpoint collisions

Duration: 5–6 hoursTarget: http://127.0.0.1:5000Tool: Burp Suite Repeater

Authorised laboratory use only. Run every activity only against the supplied VulnShop instance on 127.0.0.1. Concurrent testing can corrupt data, lock accounts and disrupt services. Never expose the deliberately vulnerable application to a public or shared network.

Overview and learning outcomes

A race condition appears when concurrent requests interact with shared application state and the server does not enforce a safe order. Several requests may observe a temporary state that should not be available to an attacker.

This lab uses one evidence-led method throughout: predict the collision, benchmark normal sequential behaviour, probe with parallel delivery, prove the final application-state impact and retest in secure mode.

By the end of this lab, you should be able to

  • Explain concurrency, shared state, race windows, temporary sub-states and TOCTOU behaviour.
  • Capture a security-critical request and organise copies in a Burp Repeater group.
  • Compare grouped requests sent sequentially and in parallel.
  • Demonstrate a one-time promotion limit overrun.
  • Demonstrate a concurrency-based failed-login rate-limit bypass.
  • Demonstrate state mixing in a single email-change endpoint.
  • Separate response anomalies from verified second-order effects.
  • Explain how atomic updates, transactions, locking, integrity constraints and idempotency prevent collisions.

Additional Lab 5

Understanding race conditions

Learn why correct sequential behaviour does not guarantee correct concurrent behaviour.

1. Core concepts and testing method

Web servers commonly process requests concurrently. Concurrency alone is not a weakness. The flaw appears when the application assumes that state cannot change between reading and using it, or when related values are created and updated outside one atomic boundary.

TermMeaning in this practical
Shared stateA database row or server-side value read and changed by more than one request.
Race windowThe short interval during which another request can interfere with an unfinished operation.
CollisionAn unintended interaction between concurrent operations on the same state.
Temporary sub-stateAn intermediate state that exists during processing but should not influence security decisions.
TOCTOUTime-of-check to time-of-use: state changes after a check but before the protected action finishes.
Network jitterVariation introduced by transport and connection handling.
Server-side jitterVariation caused by scheduling, processing, database locks or background work.
Second-order effectA later result such as a changed discount, mailbox message or authenticated session.
Atomic operationA state change that succeeds or fails as one indivisible unit.
IdempotencyRepeating the same logical operation produces no extra effect.

Why sequential testing can miss the flaw

Sequential requests let the first operation finish before the second starts. The second request sees the final state and may be rejected correctly. Parallel delivery changes the order: several requests can complete the initial check before any request records that the protected action has occurred.

Analyst judgement

An HTTP 200 response does not prove exploitation. Verify the final business effect: an excessive discount, an administrator-enabled session, a mismatched confirmation message or another state transition that should have been impossible.

1. Predict

Choose a critical endpoint that changes shared state.

2. Benchmark

Send requests sequentially and record intended behaviour.

3. Probe

Send the same group in parallel.

4. Prove

Verify final state and reduce unnecessary requests.

5. Retest

Repeat the identical test after mitigation.

Lab 1

Limit-overrun race condition

Make a nominally single-use promotion pass its pre-update check more than once.

4. Apply PROMO20 concurrently

Objective

Apply the one-time PROMO20 coupon repeatedly, reduce the £100 product to an amount within the £10 store credit and complete the demonstration purchase.

ValueLaboratory setting
ProductVulnShop Limited Edition Security Jacket
Original price£100.00
Store credit£10.00
CouponPROMO20
Intended discount£20 once
Target effectAccumulate at least £90 discount.

A. Establish the sequential baseline

  1. Open /race-condition/limit-overrun.
  2. Select Reset this lab. Confirm Discount total £0.00 and Coupon recorded as used: No.
  3. Apply PROMO20 once. Confirm a £20 discount.
  4. Apply it a second time. Confirm HTTP 409 and a coupon-reuse message.
  5. Refresh and confirm the discount remains £20.

B. Capture and prepare the group

  1. Reset the lab again.
  2. Apply the coupon once through Burp's browser so the request appears in HTTP history.
  3. Send POST /race-condition/limit-overrun/apply-coupon to Repeater.
  4. Create a group named limit-overrun.
  5. Duplicate the request until the group contains 10 identical tabs.
  6. Confirm every request uses the same Alice session cookie and code=PROMO20.
POST /race-condition/limit-overrun/apply-coupon HTTP/1.1 Host: 127.0.0.1:5000 Cookie: session=<your-current-session> Content-Type: application/x-www-form-urlencoded code=PROMO20

Do not benchmark against used state. Reset before every grouped test. Once coupon_used becomes true, later requests are rejected before entering the intended race window.

C. Compare sequence and parallel delivery

  1. Send the 10-tab group in sequence. Expect one success and nine HTTP 409 responses. Refresh and confirm £20.
  2. Reset the lab.
  3. Send the existing group in parallel. Do not send any tab individually first.
  4. Several requests should return HTTP 200 and ok: true.
  5. Refresh and inspect Discount total, Amount payable and Recent server events.
  6. If fewer than five requests succeed, reset and retry with 15–20 tabs.

D. Prove the business impact

  1. Confirm Amount payable is £10 or less.
  2. Select Purchase item.
  3. Confirm the server reports Purchase completed.
  4. Capture the final purchase state and event table. HTTP 200 responses alone are not sufficient proof.

Why the implementation fails

state = SELECT coupon_used FROM race_limit_state if state.coupon_used: reject() time.sleep(0.65) UPDATE race_limit_state SET coupon_used = 1, discount_total = discount_total + 20

The check and update are independent. Every concurrent request can read coupon_used = 0 before any update completes.

Secure design

UPDATE race_limit_state SET coupon_used = 1, discount_total = discount_total + 20 WHERE user_id = ? AND coupon_used = 0 AND purchased = 0;

The database checks and changes the state in one conditional statement. Exactly one request can update one row.

Why the implementation fails

state = read_failed_attempts(username) if state.failed_attempts >= 3: block() time.sleep(0.45) valid = compare_password(password) if valid: reset_counter() else: increment_counter()

The limiter checks the counter before authentication and updates it afterwards. Parallel requests can all observe a value below three.

Secure design

Put the threshold check, authentication decision and counter update inside one transaction. The secure SQLite implementation uses BEGIN IMMEDIATE to serialise the state transition. Add account, device and network signals, progressive delay, monitoring and MFA as defence in depth.

Lab 3

Single-endpoint email collision

Send two values to the same endpoint and investigate whether request-local and shared state become mixed.

6. Race the email-change workflow

Objective

Deliver a valid confirmation for carlos@vulnshop.local to the attacker-controlled student1@exploit.local mailbox, confirm the address and verify the resulting isolated administrative access.

ElementValue
Attacker-controlled addressstudent1@exploit.local
Invited addresscarlos@vulnshop.local
Change endpointPOST /race-condition/single-endpoint/change-email
Mailbox/race-condition/mailbox
Target mismatchDelivered to student1, but the body confirms Carlos.

A. Establish the normal workflow

  1. Confirm you remain logged in as Alice.
  2. Open /race-condition/single-endpoint and reset the lab.
  3. Submit student1@exploit.local.
  4. Open the Training mailbox.
  5. Confirm both Delivered to and Confirm the pending address show student1@exploit.local.
  6. Submit a different address sequentially and observe that only one pending address and token remain valid.

B. Capture and duplicate the request

  1. Reset the email lab.
  2. Submit student1@exploit.local through Burp's browser.
  3. Send POST /race-condition/single-endpoint/change-email to Repeater.
  4. Create a group named email-collision containing two copies.
  5. Set the first tab to student1@exploit.local.
  6. Set the second tab to carlos@vulnshop.local.
  7. Confirm both use the same Alice session and endpoint.
POST /race-condition/single-endpoint/change-email HTTP/1.1 Host: 127.0.0.1:5000 Cookie: session=<alice-session> Content-Type: application/x-www-form-urlencoded email=student1@exploit.local

C. Benchmark and trigger the collision

  1. Reset and send the two-tab group in sequence. Confirm the student1 mailbox message consistently names student1.
  2. Reset again.
  3. Send the same two tabs in parallel.
  4. Open /race-condition/mailbox in the Alice browser session.
  5. Look for a message delivered to student1@exploit.local whose body says Confirm the pending address: carlos@vulnshop.local.
  6. Record the token and request IDs. If the values match normally, reset and repeat the two-tab parallel group.

D. Confirm and verify impact

  1. Select Confirm email address inside the mismatched message.
  2. Confirm VulnShop reports Email changed to carlos@vulnshop.local.
  3. Follow the link to the race-lab administration page.
  4. Verify an administrator-authenticated session.
  5. Delete the demonstration user Carlos and confirm the lab objective is complete.

Why the implementation fails

# Request-local value delivered_to = submitted_email UPDATE pending_email = submitted_email, pending_token = token queue_confirmation_task() # Later read from shared state latest = SELECT pending_email, pending_token send_email(to=delivered_to, body_email=latest.pending_email, token=latest.pending_token)

The delivery address belongs to one request, but the body address and token can come from a later shared-state update.

Secure design

Store the requested address and token as immutable values and construct the queued message from those same values inside one transaction. Never re-read a mutable shared row while building the message.

Mitigation

Restart in secure mode and retest

Use the same request values, tab counts and delivery methods so the comparison remains fair.

Fair comparison

A mitigation is supported only when the identical test no longer produces the unintended state and normal approved functionality still works.

Defence principles

  • Make security-critical state transitions atomic.
  • Use conditional writes and verify affected-row counts.
  • Apply transactions and appropriate locks around related reads and writes.
  • Use uniqueness constraints and invariants as defence in depth.
  • Keep values from one request within a consistent snapshot.
  • Make sensitive operations idempotent where possible.
  • Log request IDs and state transitions.
  • Test mitigations under concurrency, not only with single-request unit tests.

Secure code-review questions

  • Can two requests read the same unused, unlocked or pending value?
  • Does the protected action occur before the server records it?
  • Are check and update separated by slow work, network calls or background jobs?
  • Can one request overwrite state that another request later uses?
  • Does the datastore enforce the invariant?
  • Is the operation safe when a client retries after a timeout?

Analysis questions

  1. Which shared record or variable was involved in each collision?
  2. Where did the temporary sub-state begin and end?
  3. What did the sequential baseline prove?
  4. Which response differences were clues, and which evidence proved impact?
  5. Which datastore invariant should the application enforce?
  6. Why is a transaction or conditional update stronger than another Boolean check?
  7. How could monitoring identify attempted exploitation?
  8. How might several web servers and a remote database change the result?
