Additional Lab 7

API Security Vulnerabilities

Exposed documentation, unused endpoints and broken API authorisation

Duration: 2.5–3 hoursTarget: http://127.0.0.1:5000Platform: Kali Linux and Burp Suite

Authorised laboratory use only. Perform every activity against the supplied VulnShop instance at 127.0.0.1:5000. Do not test public, university or third-party APIs without explicit written authorisation.

Overview and learning outcomes

Application Programming Interfaces allow software components to exchange data and invoke operations. Modern web applications often use REST-style endpoints and JSON behind their visible pages. An API can therefore expose functions that the normal interface does not show.

This practical develops a controlled API-testing workflow. You will establish normal behaviour, locate JSON traffic in Burp, change one request element at a time, verify the final server-side state and explain which security control failed.

By the end of this lab, you should be able to

  • Explain the difference between an API endpoint, resource, method, parameter and representation.
  • Identify JSON API traffic while browsing through Burp Proxy.
  • Use Repeater to change an API path, method, headers and JSON body.
  • Discover human-readable and machine-readable API documentation.
  • Use OPTIONS and error responses to construct a valid request.
  • Recognise broken object-level authorisation (BOLA) and broken function-level authorisation (BFLA).
  • Explain API impact on confidentiality, integrity and availability.
  • Recommend secure design and negative testing controls for REST APIs.

Real-world cyber security and job-market connection

Organisations rely on APIs for mobile apps, cloud services, payment platforms, supply chains and internal automation. Security teams must test the complete API surface, not only the buttons visible in a browser. Exposed specifications, undocumented methods and weak authorisation often lead to data exposure, account manipulation or unauthorised administrative actions.

Where you will use it: You will apply these skills as an API Security Tester, Web Penetration Tester, Application Security Analyst, Product Security Engineer, Cloud Security Engineer, DevSecOps Engineer, Security Consultant or Secure Software Developer. Employers expect you to read HTTP and JSON, map API operations, test access-control boundaries and produce evidence-led remediation advice.

Foundations

Understand the API security model

Interpret paths, resources, methods, representations, status codes and the difference between authentication and authorisation.

1. API concepts and trust boundaries

Endpoint and resource

An endpoint is the network location that receives an API request. A resource is the object represented or changed. This path identifies the price resource for product 1:

GET /api/products/1/price HTTP/1.1 Host: 127.0.0.1:5000
MethodTypical meaningLaboratory use
GETRetrieve a representation without intentionally changing it.Read a user or product price.
PATCHApply a partial change to a resource.Update an email or alter a price.
DELETERemove or deactivate a resource.Delete the fictional user Carlos.
OPTIONSReport communication options supported by an endpoint.Reveal that the price endpoint accepts PATCH.

JSON and Content-Type

JSON represents structured data as names and values. A JSON request normally declares its media type:

Content-Type: application/json { "email": "alice+api@example.local" }

Analyst habit

When an API rejects a request, read the status, headers and full JSON body before guessing. A controlled error may reveal the required content type, field name or data type.

Authentication is not authorisation

Authentication identifies the caller. Authorisation decides whether that identity may perform an action on a specific resource. Requiring a valid session does not make an API secure when every customer can delete another user or invoke an administrator-only function.

StatusMeaning in this labInterpretation
200The request was processed.Inspect the JSON and final state to confirm what changed.
400The body is malformed or a field is missing.Correct the request structure.
401No authenticated session is present.Sign in and preserve the session cookie.
403The operation is understood but refused.Assess whether the policy is consistent across resources.
404The resource is absent.Check the path and reset state.
415The media type is unsupported.Set Content-Type: application/json.

Baseline workflow

Identify and interpret API traffic

Begin with a request generated by the normal interface, then inspect the method, path, JSON body and session state.

3. Capture the normal profile API request

  1. Open http://127.0.0.1:5000/api-security/profile.
  2. Enter alice+api@example.local and select Save through API.
  3. Confirm that the page displays an HTTP 200 response and the updated JSON user object.
  4. Open Proxy → HTTP history and locate PATCH /api/user/alice.
PATCH /api/user/alice HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/json Cookie: session=<your-session-value> { "email": "alice+api@example.local" }

What this request reveals

  • The path places a user resource beneath the /api base.
  • The username is an object identifier controlled through the path.
  • JSON supplies the new representation.
  • The session cookie authenticates Alice, but the server must still authorise the object and action.

Evidence discipline

Record the unmodified request and response first. Later changes should alter only one element at a time so you can explain what caused each result.

Experiment 1

Discover exposed API documentation

Move from a known resource towards the API base, follow controlled hints and inspect the OpenAPI specification.

4. Progressively shorten the API path

  1. Send the captured PATCH request to Repeater and resend it unchanged.
  2. Remove the username, change the method to GET and send:
GET /api/user HTTP/1.1 Host: 127.0.0.1:5000 Cookie: session=<your-session-value>

The expected response is a controlled hint:

HTTP/1.1 400 BAD REQUEST Content-Type: application/json { "error": "A username is required. Try /api/user/<username>." }
  1. Shorten the path again and send GET /api.
  2. Open the returned interactive documentation locally.
  3. Open http://127.0.0.1:5000/api/openapi.json and inspect the specification.

Inspect the OpenAPI document

  • The info object describes the API title and version.
  • The paths object lists /api/user/{username}.
  • The documented operations include GET, PATCH and DELETE.
  • The PATCH definition describes application/json and the email field.

Why documentation matters. Documentation supports legitimate development, but exposed internal specifications can reveal sensitive methods, path parameters and resource structures. Documentation exposure becomes a security issue when the revealed operation also lacks effective authorisation.

Experiment 1 · Impact

Test object-level and function-level authorisation

Use the documented DELETE operation only against the resettable fictional Carlos account.

5. Delete the fictional Carlos resource

  1. Preserve Alice's authenticated session cookie in Repeater.
  2. Create and send this local request:
DELETE /api/user/carlos HTTP/1.1 Host: 127.0.0.1:5000 Cookie: session=<your-session-value>

Expected vulnerable response:

HTTP/1.1 200 OK Content-Type: application/json { "deleted": "carlos", "message": "User 'carlos' deleted" }
  1. Return to /api-security and confirm that Carlos is marked Deleted.
  2. Send GET /api/user/carlos and confirm that it now returns 404.
  3. Select Reset API laboratory and confirm that Carlos returns to Active.
QuestionFinding
Which control exists?The API requires an authenticated session.
Which controls are missing?The server does not verify object ownership or an administrator role.
Which weaknesses are demonstrated?Broken object-level and broken function-level authorisation.
Why is documentation relevant?It reveals the sensitive method and expected path parameter.
What is the consequence?An ordinary customer can deactivate another fictional user.

CIA impact

  • Confidentiality: Related unauthorised GET operations could expose user data.
  • Integrity: Another user's record is changed or deleted.
  • Availability: The deleted user can no longer access the API resource.

Secure design: Enforce ownership or administrator checks on every resource operation, separate ordinary profile functions from administrative deletion, use deny-by-default policies, protect non-public specifications and log the caller, target and outcome.

Experiment 2

Discover an unused product-price endpoint

Use OPTIONS and controlled errors to identify a state-changing method that the visible interface does not use.

6. Map the price resource and supported methods

  1. Open http://127.0.0.1:5000/api-security/product/1.
  2. In HTTP history, locate and send this request to Repeater:
GET /api/products/1/price HTTP/1.1 Host: 127.0.0.1:5000

The normal JSON response reports a price of £1337.00. The laboratory account has £100 credit, so normal checkout should fail.

  1. Change the method to OPTIONS and send:
OPTIONS /api/products/1/price HTTP/1.1 Host: 127.0.0.1:5000

Expected method discovery:

HTTP/1.1 200 OK Allow: GET, PATCH, OPTIONS Content-Type: application/json { "methods": ["GET", "PATCH", "OPTIONS"], "resource": "/api/products/1/price" }

Interpretation

The visible product page uses GET only. PATCH represents additional state-changing attack surface that the user interface does not expose.

Experiment 2 · Impact

Construct PATCH and verify the financial effect

Allow the API's controlled errors to reveal the required representation, then confirm that checkout uses the altered server-side price.

7. Change the authoritative product price

Step 1 — Send PATCH without JSON

PATCH /api/products/1/price HTTP/1.1 Host: 127.0.0.1:5000 Cookie: session=<your-session-value> price=1

Expected result: HTTP 415 with a message requiring application/json and an example price object.

Step 2 — Declare JSON but omit the field

PATCH /api/products/1/price HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/json Cookie: session=<your-session-value> {}

Expected result: HTTP 400 stating that the price parameter is required.

Step 3 — Supply the required field

PATCH /api/products/1/price HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/json Cookie: session=<your-session-value> { "price": 0 }

The vulnerable API returns HTTP 200 and stores price: 0.0.

Step 4 — Verify the second-order effect

  1. Reload the product page and confirm that it displays £0.00.
  2. Select Add to API laboratory basket.
  3. Select Attempt purchase.
  4. Confirm that checkout accepts the product for £0.00.
  5. Reset the API laboratory and confirm that the price returns to £1337.00.
ObservationSecurity meaning
The interface uses GET only.Visible UI coverage does not reveal every API operation.
OPTIONS reports PATCH.Method discovery expands the mapped attack surface.
415 explains the media type.Error detail helps construct a parsable request.
400 names the price field.Validation errors reveal the required parameter.
PATCH succeeds for Alice.A customer invokes a price-management function.

Secure design: Remove unused state-changing methods, explicitly allow methods per route, require an administrative role for price management, separate public and internal APIs, validate business constraints and add negative tests proving that a customer receives 403.

Professional workflow

Apply a repeatable API-testing methodology

Map first, vary one element at a time, test with the lowest privilege and verify the final state independently.

8. Build an evidence-led API assessment

  1. Browse the application normally and establish a baseline.
  2. Identify API-shaped paths, JSON responses and JavaScript-generated requests.
  3. Send an interesting request to Repeater.
  4. Vary one element at a time: path, method, content type, body or parameter.
  5. Read the complete response: status, headers, JSON, cookies and observable state.
  6. Test authorisation with the lowest-privileged laboratory account.
  7. Verify the effect using a separate GET request or visible page.
  8. Reset the laboratory and document the root cause, impact and remediation.

One change at a time. Changing the method, path, headers and body together prevents you from explaining which change caused the result.

  • Normal request and response.

  • Independent state verification.
  • Affected identity, resource and function.
  • CIA and business impact.

Secure design

Prevent API discovery and authorisation weaknesses

Control the complete API surface through explicit methods, resource-aware policies, safe errors and automated negative tests.

9. Map weaknesses to controls

WeaknessRequired controlVerification test
Customer can operate on another user objectObject ownership or administrator policy for every methodAlice receives 403 for another user's protected resource
Customer can invoke an administrative functionFunction-level role check and deny-by-default policyCustomer receives 403 for DELETE and price PATCH
Unused state-changing method remains enabledRemove it or explicitly allow methods per routeOPTIONS no longer advertises unnecessary methods
Internal documentation is publicly exposedRestrict non-public documentation and specificationsUnauthorised users cannot retrieve internal OpenAPI content
Errors reveal excessive implementation detailConsistent errors with enough information for legitimate clientsResponses do not expose internal structure or sensitive examples
Business values accept unsafe changesAuthorisation plus range, state and domain validationNegative and out-of-policy values are rejected without state change

Operational controls

  • Separate public catalogue APIs from internal management APIs.
  • Log the authenticated identity, action, target resource and outcome.
  • Monitor repeated method probing, unusual OPTIONS traffic and denied management calls.
  • Maintain an API inventory and remove deprecated versions and methods.
  • Test every method and object type under multiple identities.
  • Add automated regression tests to CI/CD pipelines.

API security challenge lab

10. Investigate the API without a full walkthrough

Challenge A — Method matrix

For each local endpoint, test only GET, PATCH, DELETE and OPTIONS. Record the status code, Allow header and whether application state changes.

EndpointGETPATCHDELETEOPTIONSConclusion

Challenge B — Authorisation comparison

  1. Compare GET requests for Alice and Carlos while authenticated as Alice.
  2. Explain why authentication alone does not prove that both reads are authorised.
  3. Attempt DELETE /api/user/administrator and interpret the 403 response.
  4. Propose one consistent policy for GET, PATCH and DELETE on user resources.

Challenge C — Defensive tests

Write at least three negative automated tests. State the request, expected status and security reason. Include one object-level test, one function-level test and one business-constraint test.

Hints
  • Begin with normal behaviour and preserve a valid authenticated cookie.
  • Change only one element per request.
  • A 200 response is not enough—verify the resource state through GET or the interface.
  • A secure price update should require an administrator role and valid business constraints.

Reflection

Write 150–200 words explaining why testing only visible buttons and forms gives an incomplete assessment when the API also exposes documentation or unused methods.
