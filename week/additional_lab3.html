Additional Lab 3

Fuzzing Attack

Introductory Fuzzing with Burp Intruder in VulnShop

Duration: 3 hoursTarget: http://127.0.0.1:5000Tool: Burp Suite

Authorised use only. Perform this activity only against the local VulnShop teaching application on 127.0.0.1. Use the supplied account and short payload lists. Do not test public websites, university systems or other users' accounts.

Overview and learning outcomes

Fuzzing sends a controlled set of test inputs to an application and compares the responses. Security testers use it to find unexpected behaviour, weak input validation, authentication weaknesses and inconsistent error handling.

In this lab, Burp Intruder replaces one selected password value with each entry from a small approved list. You will compare status codes, response lengths, content, redirects and cookies. You must then verify any apparent success manually.

By the end of this lab, you should be able to

  • Capture a failed authentication request with Burp Proxy.
  • Identify the username and password parameters.
  • Configure one password payload position and a Simple list payload set.
  • Run a Sniper attack against the authorised local account.
  • Establish a normal failed-response baseline.
  • Use status, length, body text, redirects, cookies and application state to identify anomalies.
  • Use Grep - Match and manual verification to avoid false conclusions.
  • Explain controls that reduce automated password guessing.

Real-world cyber security and job-market connection

Fuzzing helps professionals test how applications respond to unexpected input at scale. The important workplace skill is not only generating requests, but establishing a baseline, identifying anomalies and confirming results manually.

Where you will use it: You will use this workflow in Penetration Testing, Application Security, Security Testing, Quality Assurance and Vulnerability Research roles.

Additional Lab 3

Understand the login request and Intruder concepts

Identify the data that enters the application and choose the correct attack type.

2. Login request and success indicators

VulnShop uses a form-based POST request. A failed attempt with the authorised username resembles:

POST /login HTTP/1.1 Host: 127.0.0.1:5000 Content-Type: application/x-www-form-urlencoded username=alice&password=incorrect-password

The important parameters are username and password. The normal failure message is:

Expected output

The username or password is incorrect.

Useful success indicators

  • HTTP 302 Found instead of the normal failed response.
  • Location: /account.
  • A changed session cookie.
  • The failure message is absent.
  • The browser displays the authenticated account page.
  • A Logout option and the username alice appear.

Do not rely on one indicator. A different status, length or cookie is interesting, but it does not prove authenticated access. Confirm the final application state.

Burp Intruder concepts

Base request

The original HTTP request that Intruder modifies.

Payload position

The exact value that Intruder replaces, shown as §incorrect-password§ in Burp.

Payload set

The list of candidate inputs inserted into the selected position.

Attack typeUse in this lab
SniperOne payload set against the password field. Use this option.
Battering ramUses the same payload in several positions. Not required.
PitchforkUses several lists in parallel. Not required.
Cluster bombTests combinations across positions and can generate many requests. Do not use in this lab.

Practical

Analyse and verify the candidate

6. Analyse the results

Establish the normal failure pattern

  • Do several incorrect payloads return the same status?
  • Do they have similar lengths?
  • Do they contain the exact failure message?
  • Do they redirect to the same location?
  • Do they set similar cookies?

Investigate anomalies

An interesting result may have a different status, a redirect to /account, no failure message, a changed session cookie, account-related content or a noticeably different response time.

Add Grep - Match

  1. Open the Intruder attack settings.
  2. Find Grep - Match.
  3. Add the exact text The username or password is incorrect.
  4. Run the attack again.
  5. Investigate the response that does not match the normal failure text.

Verify manually

Method 1: Repeater

  1. Right-click the interesting Intruder request.
  2. Select Send to Repeater.
  3. Send the request.
  4. Inspect status, Location, cookies and body.
  5. Follow the redirect in the browser.

Method 2: Login form

  1. Return to /login.
  2. Enter alice and the candidate password.
  3. Submit the form.
  4. Confirm that /account opens.

Verification standard

  • The browser opens /account.
  • The page shows the username alice.
  • Account details or orders are visible.
  • A Logout control is present.
  • The failed-login message is absent.

Results interpretation process

Capture a normal request ↓ Choose one payload position ↓ Send a small controlled payload list ↓ Establish the normal response pattern ↓ Identify anomalous responses ↓ Inspect status, headers, body and cookies ↓ Verify manually ↓ Record the conclusion

Review

Defence, security impact and analyst judgement

Connect the practical result to layered controls, CIA impact and reliable security analysis.

9. Defensive controls

A real application should combine preventative, detective and recovery controls:

Prevent

  • Rate limiting and progressive delays
  • Carefully designed temporary lockout
  • Multi-factor authentication
  • Strong password and breached-password checks

Detect

  • Unusual-login monitoring
  • Repeated-failure alerts
  • IP, device and behavioural risk signals
  • Cross-account failure analysis

Recover

  • Secure session rotation after login
  • Account recovery controls
  • Incident investigation logs
  • User notification where appropriate

Security impact

Security propertyPossible impact
ConfidentialityAn authenticated attacker may access personal details, messages, orders, addresses or administrative data.
IntegrityAn attacker may change profile information, orders, preferences or transactions.
AvailabilityRepeated attempts may consume resources, trigger lockouts or deny legitimate access.

Availability caution. Large password lists are unnecessary for this lab and can create avoidable load.

Analyst judgement

Intruder automates request generation and result collection. It does not decide whether a response proves successful authentication. You must consider the baseline, status, length, headers, redirects, cookies, response content, page title, application state and manual verification.

Practical review

  1. Capture one failed login request.
  2. Mark only the password value.
  3. Run a controlled Sniper attack.
  4. Find the repeated failure pattern.
  5. Use Grep - Match to locate an anomaly.
  6. Inspect and verify the candidate manually.
  7. Explain which controls would reduce the attack.

Independent challenge lab

Identify the candidate without relying on response length and justify your conclusion.

10. Challenge: Find the anomaly through response content

Scenario

Your response lengths vary because the application generates different session data. You therefore cannot use length as your main sorting method.

Your tasks

  1. Configure Intruder to highlight the standard failure message.
  2. Run the approved local payload list.
  3. Identify the candidate without sorting by response length.
  4. Explain which response characteristic first revealed the candidate.
  5. State whether that characteristic alone proved success.
  6. Verify the candidate through Repeater and the browser.
  7. Explain which defensive control would most effectively slow this activity.
  8. Assess whether the error message reveals whether the username exists.
  9. Explain how rate limiting would change your test plan.

Challenge hints

  • Most incorrect passwords should match the exact failure text.
  • A 302 response often has little body content. Inspect its Location header.
  • Manual access to /account provides the strongest verification.
  • Stop if the local application begins to throttle or lock the account.

Challenge notes

Reflection

Write approximately 200 words answering: Burp Intruder identified an unusual response, but why did you still need to verify it manually? Discuss false positives, dynamic content, redirects, cookies, response-length variation and changes in application state.
