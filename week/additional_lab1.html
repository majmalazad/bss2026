Additional Lab 1

Mastering Burp Suite

Proxy, Target, Repeater, Intruder, Inspector and supporting tools

Duration: 4–5 hoursTarget: http://127.0.0.1:5000Platform: Kali Linux

Authorised laboratory use only. Use Burp Suite only against the supplied local VulnShop instance or another system for which you have explicit written permission. Scope settings help control tools; they do not provide legal authorisation.

Overview and learning outcomes

Burp Suite combines manual and automated tools for web application security testing. This practical starts with the browser and intercepting proxy, then builds a repeatable process for mapping an application, selecting important requests, testing one hypothesis at a time and recording conclusions supported by evidence.

By the end of this lab, you should be able to

  • Launch Burp Suite and choose a suitable temporary or saved project.
  • Explain how Burp Proxy sits between a browser and an authorised target.
  • Intercept, inspect, edit, forward and drop HTTP requests safely.
  • Use HTTP history, filters and target scope to reduce noise.
  • Use the Target site map to identify endpoints, methods and parameters.
  • Create a baseline and test controlled changes in Repeater.
  • Configure a small Sniper attack in Intruder and interpret outliers.
  • Use Inspector, Decoder, Comparer, Logger and Organizer.
  • Apply the cycle: define scope, map, analyse, test, verify and record.
  • Separate a response anomaly from a confirmed security weakness.

Real-world cyber security and job-market connection

Burp Suite provides the core workflow used in many professional web assessments: capture traffic, define scope, map endpoints, modify requests, automate small tests and verify evidence. Mastery comes from understanding HTTP and analyst judgement, not only knowing where tools are located.

Where you will use it: These capabilities are central to Web Penetration Tester, Application Security Analyst, Security Consultant, Vulnerability Researcher and Product Security roles.

Preparation

Start VulnShop and Burp Suite

Keep the target local, begin with a temporary project and verify that Burp records browser traffic.

1. Prepare the laboratory

Step 1 — Start VulnShop

cd Desktop/vulnshop chmod +x run.sh ./run.sh

Keep the terminal open throughout the lab. Confirm that the local application loads at http://127.0.0.1:5000.

Step 2 — Start Burp Suite

burpsuite
  1. Select Temporary project.
  2. Select Use Burp defaults.
  3. Select Start Burp.

Step 3 — Complete start-up checks

  • The Dashboard opens without a critical error.
  • Proxy → Intercept contains an Open browser button.
  • VulnShop opens directly at http://127.0.0.1:5000.
  • No other program uses Burp's proxy listener port.
  • The VulnShop terminal remains open.

Core concept

Understand the browser–proxy–target model

Burp records and optionally pauses messages between your browser and the authorised application.

2. Observe traffic through Burp Proxy

Launch Burp's browser

  1. Open Proxy → Intercept.
  2. Set Intercept is off for normal navigation.
  3. Select Open browser.
  4. Open http://127.0.0.1:5000.
  5. Return to Proxy → HTTP history and confirm that local requests appear.

Why begin with interception off?

Modern pages generate many background requests. HTTP history continues recording traffic when interception is off, so you can browse normally and pause only the one action that you need to inspect.

Capture one controlled request

  1. Navigate to the page immediately before a harmless action, such as a product search.
  2. Switch Intercept is on.
  3. Perform the action once.
  4. Read the request line, host, cookies, content type and parameters.
  5. Select Forward to continue or Drop to cancel.
  6. Switch interception off after the controlled capture.
Request elementQuestion to ask
MethodDoes the request retrieve information or change state?
Path and queryWhich endpoint and values come from the user?
HeadersWhich host, origin, referer and content type are present?
CookiesDoes the request carry session or preference state?
BodyIs data form-encoded, JSON, XML, multipart or another format?

Browser appears frozen? Check whether Proxy is holding a request. Forward or drop it, then return interception to off.

Message editor views

Raw, Pretty, Hex and Render

  • Raw: exact HTTP-style syntax.
  • Pretty: formatted JSON and supported structures.
  • Hex: byte-level representation.
  • Render: browser-like response view; not a substitute for browser verification.

Inspector

Inspector presents query parameters, body parameters, cookies, headers and request attributes as structured values. It can decode a value for editing and re-encode it in the request.

Use the context menu as the tool bridge

Right-click an interesting request, response or selected value and choose Send to Repeater, Intruder, Decoder, Comparer or Organizer. Transferring the original message preserves headers, cookies and encoding that manual retyping may lose.

Working rule

Do not manually reconstruct a request when Burp can transfer the captured message directly.

Mapping

Use HTTP history, scope and the site map

Reduce background noise and build a structured view of the authorised application.

4. Locate and map meaningful traffic

Locate an interesting request

  1. Browse VulnShop with interception off.
  2. Open Proxy → HTTP history.
  3. Sort so that recent requests are easy to find.
  4. Filter for in-scope traffic, requests with parameters or selected MIME types.
  5. Select a request and inspect both message panels.
  6. Search for a path, parameter or response message.
  7. Add a comment or highlight when useful.
ColumnHow to interpret it
HostSeparates the target from third-party services.
MethodShows GET, POST, PUT, DELETE or another operation.
URLShows the path and query values.
StatusShows the server response such as 200, 302, 403 or 500.
LengthProvides an anomaly clue, not proof of a weakness.
MIME typeDistinguishes HTML, JSON, images and scripts.

Add the local target to scope

  1. Open Target → Site map.
  2. Locate 127.0.0.1:5000.
  3. Right-click the host and select Add to scope.
  4. Hide or exclude out-of-scope traffic when prompted.
  5. Return to HTTP history and apply the in-scope filter.

Scope is not authorisation. Adding a host to scope only filters Burp's work. It does not grant permission to test the host.

Manual mapping checklist

  • Browse before and after authentication when approved credentials exist.
  • Visit search, product, basket, account, profile and error-handling functions.
  • Identify requests that change state and record their methods.
  • Review JavaScript and API traffic for hidden endpoints.
  • Look for identifiers, filenames, redirect locations, tokens and role values.
  • Record functions that appear only after a particular sequence.

Manual testing

Reissue requests with Repeater

Create a baseline, change one value and verify whether the application effect is meaningful.

5. Test one hypothesis at a time

  1. Select a request with a parameter you understand in HTTP history or the site map.
  2. Right-click and choose Send to Repeater.
  3. Open Repeater and select Send without changes.
  4. Record the status, response length, key headers, response content and application state.
  5. Change one parameter value only.
  6. Send the request again and compare the result.
  7. Use tab history to move between request and response pairs.
  8. Restore the baseline before testing another hypothesis.

Verification

Response features to compare

  • Status code and reason phrase.
  • Response length and content type.
  • Location header for redirects.
  • Set-Cookie and authentication state.
  • Error messages, JSON fields and rendered content.
  • Application state after a refresh or a second request.
  • Response time, allowing for normal variation.

Manual verification

A changed status code or response length is only an anomaly. Confirm the security effect in the application: access the protected page, inspect a changed record, repeat the action or compare with a known failure.

Controlled automation

Automate a small input test with Intruder

Use one payload position, a short list and manual verification of any outlier.

6. Configure and interpret a Sniper attack

Configure the attack

  1. Send a tutor-approved search, filter or page request to Intruder.
  2. Open the attack tab and select Positions.
  3. Clear automatically selected payload markers.
  4. Highlight only the value that you want to vary.
  5. Select Add § and confirm that one position remains.
  6. Choose Sniper.
  7. Open Payloads and choose Simple list.
  8. Add no more than ten harmless values.
  9. Review target, request count and settings, then start the attack.
GET /search?q=§laptop§ HTTP/1.1 Host: 127.0.0.1:5000

TypeConceptual useBeginner guidance

Analyse results

IndicatorWhy it mattersLimitation
StatusRedirects or errors may differ.Success and failure may share a status.
LengthOutliers may reveal different behaviour.Dynamic content changes length.
Grep matchHighlights known success or failure text.Text can be absent for unrelated reasons.
TimeMay reveal processing differences.Network and server jitter create noise.
Cookies or headersA session or redirect may matter.Failures can also set cookies or redirect.

Rate and account safety. Keep lists small and use only instructor-approved laboratory accounts. Automated requests may trigger rate limiting, lockout or service instability.

Verify the outlier

  1. Select an interesting row.
  2. Send it to Repeater.
  3. Resend the request manually.
  4. Inspect status, headers, body and application state.
  5. Record whether the difference represents a confirmed weakness, normal behaviour or a false positive.

Toolchain

Use Inspector and supporting Burp tools

Move evidence between tools as the investigation becomes more focused.

7. Transform, compare, trace and preserve

Inspector

View query parameters, body values, cookies and headers in a structured panel. Edit a decoded value and confirm that Burp updates the raw message correctly.

Decoder

Apply encoding, decoding and hashing transformations one at a time. Record the sequence so that you can reverse it accurately.

Comparer

Compare two messages at word or byte level to isolate a subtle token, role, error or content difference.

Logger

Trace requests generated by Burp tools and extensions. Use it when HTTP history does not show the full source of a request.

Organizer

Store read-only copies of important request and response pairs with notes and highlights.

Sequencer

Analyse a sample of tokens intended to be unpredictable. Statistical results do not replace review of token generation, scope and invalidation.

Common encoding clues

ClueLikely formatInterpretation
%2F or %3DURL encodingEncoded slash or equals sign.
&lt; or &#x27;HTML encodingMarkup-sensitive characters represented as entities.
Long alphanumeric string ending with =Possible Base64Decode to determine whether it contains readable or binary data.
Three dot-separated segmentsPossible JWTHeader, payload and signature; decoding does not verify the signature.
Mostly hexadecimal pairsHexadecimalConvert carefully and preserve byte boundaries.

Decoded does not mean trusted

Encoding changes representation. It does not provide encryption, validation or authenticity. A readable value may still rely on a signature, MAC or server-side check.

Professional practice

Apply a structured penetration-testing workflow

Use an evidence-led cycle instead of jumping directly to payloads.

8. Define, map, analyse, test, verify and record

1. Define scope

  • Confirm explicit authorisation.
  • List permitted hosts, ports, accounts and times.
  • Record prohibited actions.
  • Add only authorised targets to Burp scope.

2. Map

  • Browse user journeys with interception off.
  • Review history, JavaScript, APIs and the site map.
  • Use approved roles and states.
  • Record sensitive and state-changing functions.

3. Analyse

  • Identify parameters, headers, cookies, IDs and filenames.
  • Prioritise identity, session and access-control functions.
  • Compare client-side controls with server enforcement.
  • State a clear hypothesis.

4. Test

  • Preserve a baseline.
  • Change one factor in Repeater.
  • Use Intruder only where a small repeated test adds value.
  • Preserve encoding with Inspector or Decoder.

5. Verify

  • Reproduce from a clean baseline.
  • Confirm the effect in application state.
  • Exclude caching, dynamic data and expired sessions.
  • Retain minimal supporting evidence.

6. Record

  • Write the endpoint, method and prerequisites.
  • Explain impact on confidentiality, integrity or availability.
  • Redact sensitive values.
  • Recommend a server-side correction and retest method.

Scanner responsibility [Professional only]

Burp Scanner combines crawling and auditing. Automated findings remain hypotheses until you reproduce the behaviour manually, assess business impact and remove false positives. Community Edition users can complete the full manual workflow without Scanner.

PhasePurposeAnalyst responsibility
CrawlDiscover reachable content and navigation.Check whether authenticated and state-dependent functions were reached.
AuditSend security checks to insertion points.Review evidence and reproduce potential issues manually.
Issue reviewOrganise potential findings.Remove false positives, duplicates and unsupported impact claims.

Handle reports as sensitive data. Reports can contain internal URLs, session material, personal information and exploit details. Store and share them only through approved channels.

Integrated exercise

Complete the VulnShop Burp workflow

Bring the tools together without targeting a particular vulnerability.

9. Guided practical

Part A — Start and map the target

  1. Start VulnShop and keep its terminal open.
  2. Launch Burp's browser with interception off.
  3. Visit at least five VulnShop pages.
  4. Identify hosts, methods, paths, statuses and MIME types.
  5. Add 127.0.0.1:5000 to scope.
  6. Draw a simple map of the visible application functions.

Checkpoint A

Identify one read-only request, one state-changing request, one request containing user input and one request carrying a session cookie.

Part B — Capture and interpret

  1. Choose one harmless action.
  2. Turn interception on immediately before the action.
  3. Identify method, path, host, parameters, cookies and content type.
  4. Forward the request and turn interception off.
  5. Review the response in HTTP history.

Part C — Test in Repeater

  1. Send the request to Repeater.
  2. Create an unchanged baseline.
  3. Change one non-destructive value.
  4. Compare status, length, headers, body and state.
  5. Restore the baseline and test a second value.
  6. Write a conclusion that distinguishes an observation from a verified weakness.

Part D — Small Intruder exercise

  1. Send a search or filter request to Intruder.
  2. Mark only one input position.
  3. Use Sniper with no more than ten harmless values.
  4. Identify the repeated baseline pattern and any outlier.
  5. Send the outlier to Repeater and verify it manually.

Part E — Supporting tools

  1. Decode one encoded value with Inspector or Decoder.
  2. Compare two similar responses in Comparer.
  3. Save one important message in Organizer with a note.
  4. Use Logger to locate a request generated by Repeater or Intruder.

  2. Check the exact URL and route.

Independent work

Challenge lab

Demonstrate that you can choose and combine Burp tools without following a fixed request-by-request script.

10. Mastering Burp Suite challenge

Challenge A — Attack-surface map

Map VulnShop as an unauthenticated user and as Alice. Identify functions, methods, user inputs, session-dependent routes and state-changing requests.

Challenge B — One-input investigation

Select a harmless parameter. Establish a baseline, test three justified values in Repeater and state whether any result represents a weakness or normal validation.

Challenge C — Controlled fuzzing

Create a ten-value Sniper attack for one authorised input. Define the baseline pattern, identify an outlier and verify it manually.

Challenge D — Toolchain evidence

Move one message through Proxy, Repeater, Decoder or Inspector, Comparer and Organizer. Explain why each transfer supported your investigation.

Challenge E — False-positive review

Create or locate an apparent anomaly caused by a redirect, dynamic token or changing length. Show why it does not prove a vulnerability.

Challenge F — Mobile extension design

Describe how an authorised Android or iOS device would route application traffic through Burp. Address network reachability, proxy settings, CA trust and certificate pinning.

Challenge deliverable

Submit or retain a concise learning record containing:

  • Scope and authorisation boundary.
  • Application map and selected endpoint.
  • Baseline request and response.
  • Controlled modification or payload set.
  • Comparison evidence.
  • Manual verification.
  • Conclusion and alternative explanation.
  • Relevant CIA impact and server-side remediation where a weakness exists.

Reflection prompt

Burp identified an anomalous response. Explain the additional evidence required before you can report a confirmed vulnerability. Discuss baselines, repeatability, headers, cookies, content, application state and alternative explanations.
